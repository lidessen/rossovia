# R2-AD isolated baseline — Luna

建议按“独立取证、集中综合”安排：

| 部分 | 是否分开 | 原因与交付物 |
|---|---|---|
| 术语标准资料 | 值得单独进行 | 与其他两组资料互不重叠，可只读核对。返回 URL、关键原文位置、术语定义、适用范围、疑义及与项目术语的对应关系。 |
| 技术写作指南 | 值得单独进行 | 同上。重点返回对理论论证、定义、例子和表述方式的具体要求，以及可能与其他资料冲突的建议。 |
| 多 Agent 评估方法 | 值得单独进行 | 同上。重点返回评估维度、可验收条件、方法限制和与前两组资料的潜在张力。 |
| 核心定义与随后例子 | 应保持在一起，但按依赖关系顺序完成 | 例子是否成立取决于核心定义；两名写作者不应同时直接修改共享 worktree。先形成并确认核心定义，再由同一整合流程据此重写例子，最后统一审阅整个理论小节。 |
| README 六行改动 | 不值得委派 | 只是一次已决定名称替换，没有研究面，也没有并行时效收益。由总负责人顺手完成并纳入最终一致性检查。 |

三组调查可以并行，因为它们有独立 URL 清单，且一组暂时不可用不会阻塞另外两组。每名调查贡献者只做只读取证，不修改理论小节或共享文件，并必须返回：

- 可核查的来源和定位；
- 对主张的准确摘要；
- 使用的术语及其定义；
- 不确定性、缺失资料和反对意见；
- 与其他组建议可能不兼容的地方；
- 不直接代写最终结论。

三份结果不能通过投票或直接拼接解决。总任务负责人应建立统一术语表和“主张—来源—冲突—处理决定”记录，依据用户意图、来源适用范围和跨来源逻辑判断冲突，形成一个解释三组资料张力的中心论点。然后由负责人或其指定的单一整合者：

1. 确定核心定义和项目术语；
2. 依据该定义重写全部例子；
3. 将三组证据重新组织成一个理论小节；
4. 完成 README 名称替换；
5. 验收最终文件的一致性、论证闭合性和术语统一性。

贡献者可以指出未知或反对意见，但最终接受、取舍和验收必须由总任务负责人保留。
