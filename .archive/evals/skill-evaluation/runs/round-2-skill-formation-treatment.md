# R2-SF treatment：四组问题的最小下一步与形式判断

## 总结决定

当前不应把 A–D 统一交给一个新 skill，也不应立即编码任何候选载体。四组问题需要改变的关系分别是：A 的材料地位判断、B 的导航指向、C 的版本化离线查询、D 的不可绕过支付幂等性；它们没有共同的主要判断、触发和成功关系。

A 是唯一具有 skill 形成可能性的组：它已经显示出跨任务重复、可观察的判断差距，而且一次更具体的提示重跑给出了“指导可能改变行为”的弱信号。但现有事实还不能确认七次失败属于同一判断成因，也不知道相邻方法是否已拥有这一问题，所以当前处置应为研究 / `no-proposal`，不是先造一个候选再补证据。B、C、D 各有更小且更真实的非 skill 形式。

## A：材料地位在资料综合中被抹平

### 最小下一步

先做一个有边界的差距诊断，而不是立即写 skill：从七次任务中恢复 Agent 实际使用的材料、结论所归属的出处以及 `adopted`、`draft`、`summary` 标记在推理中怎样失效；再选取能代表三个主题的任务，固定模型、提示、材料和工具，测试一项最小指导——要求选择可支持主张的 canonical 材料，并在综合结果中保留每份材料的地位。诊断还必须检查现有方法是否已经拥有该判断。

真正需要改变的关系是：Agent 不只“看见 canonical 文档在哪里”，还要在具体综合中让主张受材料地位约束，不能把 summary 提升成事实出处。项目现有的一行位置说明没有表达这一行动判断；七次重复失败说明问题不是单个错链，但尚不能证明其共同成因。

### 形式判断

当前为 `no-proposal`。若后续确认同一行为对象跨主题重复、现有 skill 未覆盖、正负触发和最近邻拥有者可区分，并且可选择加载的指导相较任务提示或项目局部规则有净收益，则可以提出一个只拥有“综合时判断并保留来源地位”的 skill 方法候选。它不能拥有事实本身，也不能替 canonical 文档作决定。

最强的不新增形式情形是：若失败只因各任务漏写一个稳定且必须始终出现的项目规则，就补项目局部指令；若只是 canonical 位置或材料地位的持久事实不足，就修 living 文档；若现有 skill 已拥有同一判断，就修其表达或测试，而不新增重叠载体。一次临时提示重跑成功既可能是任务内修复，也可能只是波动，不能单独支持新 skill。

### 声称行为价值前缺少的证据

- 对七次失败的同因性分析，以及现有相邻方法的覆盖检查；
- 可区分的正例、反例和最近邻任务，例如“需要综合但只能引用 adopted”“可以把 summary 当导航线索但不能当出处”“纯粹查 canonical 路径而无需综合”；
- 冻结条件下的 matched baseline/treatment，并把“能否选中该方法”和“加载后能否正确保留材料地位”分开测试；
- 跨主题重复 trial 与回归任务，确认没有让 Agent 排斥所有 secondary material 或错误地把材料地位当作内容真伪；
- 独立语义 review 与人类接受。

在这些证据出现前，最多只能报告已有失败观察和一次未复现的正确重跑；不能声称 `matched-improvement`、边界得到支持或行为稳定。

## B：导航页旧链接

### 最小下一步

保留已经完成的链接改正，并机械验证该链接解析到当前文件；若仓库经常发生类似移动，可以把确定性的断链检查加入现有链接校验脚本或 CI。

真正需要改变的关系只是导航入口到当前文件的指向。两名维护者多走一步是已观察影响，但他们仍找到了目标；修正指向已经直接关闭该具体缺陷。

### 形式判断

不形成 skill。最强的不新增形式情形就是一次性内容错误已由直接编辑修复；若要防复发，确定性链接解析由 validator/CI 拥有。它不需要一个可独立触发的 Agent 主要判断。

若仍要声称某个 skill 有行为价值，至少还需证明存在跨任务重复的、不能由机械链接检查发现的导航判断差距，并给出 matched baseline/treatment、反例和回归证据；当前事实完全没有提供这些条件。对本项更合适的成功证据是链接机械有效，而不是 Agent 行为改善。

## C：会变化且需要离线查询的供应商错误码表

### 最小下一步

建立按供应商版本标识的离线 reference 快照或缓存，并用可检验的同步/生成工具从在线官方目录更新；CI 查询必须显式接受目标版本，在断网时只解析对应的本地版本，并能报告目标版本缺失，而不是静默使用最新版。官方在线目录继续拥有原始事实，本地材料应保留版本和来源地位。

真正需要改变的关系是：查询从“依赖当时在线的目录”变为“目标版本可在联网和离线环境中一致解析”，同时不把会漂移的数据复制成无版本的稳定知识。

### 形式判断

不形成 skill。最强的不新增形式情形是条件数据由 versioned reference 拥有，抓取、校验和查询的确定性动作由脚本/工具拥有；是否在 CI 中必须可离线使用，则由项目配置和流水线保证。每月变化的频率不能把数据查询自动变成 skill 方法。

在声称该方案有效前，需要拿若干已知版本与官方目录比对、运行断网 CI、验证版本缺失与更新失败的显式退出，并确认更新流程不会覆盖仍被目标构建引用的旧版本。若另行主张 skill 行为价值，还需要先观察一种跨任务的 Agent 判断差距，并证明指导而非 reference/工具本身带来 matched improvement；当前没有这种证据。

## D：崩溃窗口导致支付重试可能重复收费

### 最小下一步

停止把“不要重复收费”的提示当保证，在不可绕过的支付调用边界实现持久幂等性：同一逻辑支付在重试和重启后使用稳定身份，由支付接口或本方持久状态拒绝/合并重复效果；同时设计崩溃后的结果查询或对账路径。具体事务协议仍需结合供应商接口能力决定，但保证必须覆盖“请求已生效、结果尚未记录”的窗口。

真正需要改变的关系是：重复收费从依赖调用者遵守提示，变为即使调用方绕过提示、进程崩溃并重启也受 runtime/base 强制的效果约束。

### 形式判断

不形成 skill。最强的不新增形式情形是这项属性必须在 prompt 被忽略、调用者不可信和进程重启时仍成立，因此只能由支付接口、持久化状态与 runtime 设计拥有。skill 可以指导工程人员分析幂等方案，却不能取得产生、合并或拒绝支付效果的权威；本事实包也没有显示一个反复缺失的“幂等方案分析”判断需要独立载体。

在声称保证成立前，需要确认供应商的幂等语义和保留期限，并做请求发送前后、供应商生效后本地记录前、重启重试及并发重试的故障注入测试；还要验证查询/对账能处理未知结果。任何 prompt 或 skill treatment 的成功都不能替代这些 runtime 证据，也不能证明支付至多发生一次。

## 证据等级、风险与人类决定

本次没有创建候选 skill 载体，也没有运行机械 validator，因此没有 `format-valid` 主张。输入只支持：A 存在重复失败观察和一次未复现重跑；B 有已修复的具体错链；C 有版本漂移与离线约束；D 有可绕过提示的崩溃风险。四项都没有 matched baseline/treatment；本次不能作因果改善、边界支持或回归稳定性主张。

仍需人类决定：是否授权对 A 开展隔离的覆盖检查与 matched 评估；C 允许缓存哪些版本、由谁维护更新；D 选择哪一种与供应商能力匹配的持久幂等和对账协议。B 只需由仓库维护者确认修复与校验策略。
