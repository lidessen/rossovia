# 第二轮 skill 行为 probe

本轮只预注册试题，不运行、不评分。目标是观察候选 skill 载体所表达的方法在一次激活中是否改变判断或行动，而不是是否让答案更长、更整齐或更像 skill 文档。

每项试验只把该项的“给 runner 的逐字任务”和“原始事实包”交给 runner；不要把“评审预注册”交给 baseline 或 treatment。baseline 与 treatment 必须使用两个互不读取对方输出的新鲜上下文，但采用同一 runner 配置。treatment 只能比 baseline 多加载该项指定的候选 skill 载体，并在该任务中发生一次激活。若平台不能核实这一点，结果只能记为行为观察。

候选 skill 载体可以记录理论血统，但 treatment 不得回读配套 P、theory、research 或 archive 才取得行动方法。本轮把“仅凭候选 `SKILL.md` 与同一份 task/source 能否完成目标判断”作为共同可观察关系：若输出要求先补读 P 才能行动，候选载体在这项 probe 中不自足；这不等于允许 runner 猜补原始事实包没有给出的事实。

## R2-SF — 是否形成 skill

<!-- R2-SF-TASK-BEGIN -->
### 给 runner 的逐字任务

团队想把下面四组问题统一交给一个新 skill 方法。请逐组决定最小的下一步，并判断其中是否有任何一组值得形成 skill 方法、再编码为可选择加载的候选载体。说明每项真正需要改变的关系、最强的不新增形式情形，以及在声称有行为价值前还缺什么证据。不要因为问题后果严重或出现次数多，就默认需要同一种形式。
<!-- R2-SF-TASK-END -->

<!-- R2-SF-SOURCE-BEGIN -->
### 原始事实包

- A：七次跨三个主题的资料综合中，Agent 都看见了页面顶部的 `adopted`、`draft`、`summary` 标记，却在结论里把 summary 当成事实出处。任务提示各不相同，项目已有一行文字指出 canonical 文档的位置，但没有说明在具体判断中如何选择材料和保留材料地位。一次失败后，分析者临时补了一句更具体的提示；该任务单次重跑正确，尚未复现。
- B：导航页的一条链接仍指向旧文件。两名维护者因此多走了一步，但都通过相邻链接找到了当前文件；链接改正后尚未再观察到误导。
- C：供应商大约每月调整错误码表。在线的官方目录可查询且带版本；本项目约三成 CI 运行不能联网，离线时仍需按目标版本查字段。
- D：支付进程在发出请求后、记录结果前崩溃，重启后可能再次收费。现有提示写着“不要重复收费”，但调用方可以绕过提示直接调用接口。

除此以外，不知道 A 是否同属一个成因，不知道现有其他方法是否已覆盖 A，也没有任何 matched baseline/treatment。
<!-- R2-SF-SOURCE-END -->

### 评审预注册（不要给 runner）

- 正例：A 最多进入 skill 方法及其载体的候选判断；对象是反复出现的、任务条件下的材料选择与来源地位保持，不是资料本身。
- 边界：A 的单次修正尚不能证明 skill 有增益；若成因只是 canonical 标记缺失、现有方法已拥有该判断，或 matched 行为不变，应不新建或降级。
- 最近邻：B 是局部文档修正；C 是带版本和来源关系的条件性事实供应；D 需要跨重启和绕过路径仍成立的机制。
- 重大缺陷：把四项合并为一个 skill；把后果严重等同于 skill 准入；把单次重跑当成改善证据；让方法承担 D 的硬保证。
- 可观察差异：候选载体所表达的方法若有价值，应让 treatment 更稳定地区分“候选、直接修正、事实供应、机制保证”，并保留 A 的未决证据，而不是增加术语或篇幅。

## R2-CA — 先区分概念，再决定名称

<!-- R2-CA-TASK-BEGIN -->
### 给 runner 的逐字任务

项目记录把下列状态都写成“完成”，导致交接时互相替代。请只从事实包建立真正需要的概念区别：先用临时指称说明每个概念的直接上位概念、区别特征、包含项、最近排除项和一个可证伪例子；检查这些区别是否会改变交接判断；边界稳定后再提出名称。不要为了给每条记录配一个词而制造无用概念。
<!-- R2-CA-TASK-END -->

<!-- R2-CA-SOURCE-BEGIN -->
### 原始事实包

- 记录 1：转换命令返回 0，但输出文件缺少 `owner` 字段。
- 记录 2：另一个文件通过确定性的 schema checker，但内容引用了已经撤回的资料。
- 记录 3：独立 reviewer 对照当前资料后认为可以发布，并给出带保留意见的建议；他没有发布权限。
- 记录 4：请求中指定的负责人签字接受，但发布队列尚未运行。
- 记录 5：发布队列把内容送到生产环境，随后负责人撤回接受；生产环境仍保留旧内容。
- 交接规则只要求下一位维护者判断：是否需要重新运行命令、修复结构、补做语义审查、等待有权者决定，或处理外部已发生的发布效果。

不知道团队最终偏好中文名还是英文名，也不知道是否要保留“完成”作为非正式总称。
<!-- R2-CA-SOURCE-END -->

### 评审预注册（不要给 runner）

- 正例：至少区分执行结果、确定性结构符合、语义建议、有权接受和外部发布效果；区别必须支持不同的下一步。
- 边界：不应仅因五条记录而机械产生五个平行术语；撤回后的接受状态与仍存在的外部效果要按关系和时间解释。
- 最近邻：命令成功不能替代产物符合；符合不能替代知源判断；建议不能取得接受或发布效果。
- 重大缺陷：先定名称再回填定义；把 reviewer 建议命名为接受；把发布事实当成当前接受；定义不能改变交接判断。
- 可观察差异：treatment 应更可靠地从对象、特征和关系形成最小概念组，最后才命名，而不是只把五条记录换成五个近义词。

## R2-FS — 选择最小真实形式

<!-- R2-FS-TASK-BEGIN -->
### 给 runner 的逐字任务

团队建议新建一个 `knowledge-system/`，为下列每项各放一个文件。请逐项判断是否真的需要新载体、需要什么最小形式，以及什么不应由该形式承担。说明事实或方法从哪里取得地位、预期存在多久、谁会在什么情形使用；最后再检查普通文件或目录位置。不要先从目录整齐程度反推设计。
<!-- R2-FS-TASK-END -->

<!-- R2-FS-SOURCE-BEGIN -->
### 原始事实包

- A：一段关于“什么算重复行为差距”的解释，过去一年因认识变化修订两次；维护者和设计 Agent 都会引用它来解释后续决定。
- B：十二次互不相同的任务都需要 Agent 在行动前判断要不要加载额外资料；其他任务不需要这套判断。团队希望把这套 skill 方法编码为选择性加载的载体，只在相关任务中加载载体并激活方法。
- C：外部供应商每周变更字段和错误码。官方接口能返回目标版本；本地 CI 有三成时间离线，但必须重现当时使用的版本。
- D：这个仓库的任何任务都不得改动 `vendor/`；新 Agent 从任意子目录进入都必须看见这条边界。
- E：四十个文件要从旧目录搬到新目录，引用修完并通过检查后，这项工作即结束。
- F：一个发布调用在进程重启后可能重复产生外部效果，即使任务文字写了“只发一次”。
- G：导航页需要展示 A 的三句摘要；它可以从 A 自动生成，不增加新判断。
<!-- R2-FS-SOURCE-END -->

### 评审预注册（不要给 runner）

- 正例：A 是耐久解释；B 是选择性加载的 skill 载体，载体表达按任务激活的方法。
- 边界：E 是有限工作；G 是可重建视图；两者不应因“也有文件”而成为独立长期权威。
- 最近邻：C 保存外部版本事实；D 必须在项目范围持续可见；F 是跨重启的效果机制。它们不应被 B 吸收。
- 重大缺陷：接受统一新子系统；让本地副本冒充 C 的事实权威；让选择性方法拥有 D 或 F；把路径选择当成主判断。
- 可观察差异：treatment 应改变载体准入、转交或拒绝判断，而不是只给同一批文件更漂亮的名称。

## R2-HW — 为具体读者形成完整论述

<!-- R2-HW-TASK-BEGIN -->
### 给 runner 的逐字任务

一位熟悉仓库、但没有参与近期设计的维护者问：“一个格式完全合格的 skill 载体，为什么仍可能应该删除？”请根据事实包写一段可直接放进设计说明的中文解释。让读者能够理解判断链和当前不确定性；不要写成字段清单、检查表或七个小标题。运行验证器的具体命令已在操作手册中，不必复制。
<!-- R2-HW-TASK-END -->

<!-- R2-HW-SOURCE-BEGIN -->
### 原始事实包

- 项目把 skill 看成方法；方法由按任务选择加载的载体表达。文件包是载体，不是需要被改善的行为对象。
- 九个候选 skill 载体都通过了 frontmatter、目录名和链接检查。
- 在已有的行为观察中，有三个候选载体所表达的方法没有改变目标判断；其中两个载体还会在相邻任务上被误激活。
- 一个候选载体经边界修订后，Agent 在一次激活对照中作出了此前没有作出的正确拒绝；该次运行的模型和 harness 是否完全相同没有被核实。
- 候选 skill 载体可被改写、拆分、合并、降为别的形式或删除；项目没有“文件创建后必须保留”的规则。
- 目前不知道多少次 matched trial 足以推广到其他模型和任务，也不知道上述三个未改变目标判断的候选载体所表达的方法，是否在尚未覆盖的任务上有价值。
<!-- R2-HW-SOURCE-END -->

### 评审预注册（不要给 runner）

- 正例：围绕“格式只证明载体可用，不证明方法有行为价值”形成连贯解释，并自然导向多种处置。
- 边界：不得把一次未完全 matched 的正确拒绝写成已证实改善，也不得由三个未改变目标判断的候选载体推出所有这类方法普遍无效。
- 最近邻：验证器命令属于操作说明，不是这段理论解释的论证主体。
- 重大缺陷：目录式罗列；丢失关键不确定性；把文件存续当目标；为简短而省略为何删除合理的中间关系。
- 可观察差异：treatment 应改善读者能否恢复论证和证据限度；华丽、顺滑或更长本身不算行为改善。

## R2-AE — 在压缩偏好下保留 Agent 行动关系

<!-- R2-AE-TASK-BEGIN -->
### 给 runner 的逐字任务

请把事实包写成一份可直接交给研究 Agent 的任务。产品的默认提示偏好“尽量短，通常不超过 80 个汉字”，但该偏好没有权限删除业务要求。输出应尽可能紧凑，同时仍让 Agent 能在真实上下文中判断、行动并返回可验收结果；不要执行研究。
<!-- R2-AE-TASK-END -->

<!-- R2-AE-SOURCE-BEGIN -->
### 原始事实包

- 研究对象是 ISO 704 的 concept/definition 关系与 W3C SKOS 的 concept/label 关系。
- 只可使用两者的官方页面和那些页面直接指向的规范性材料；二手教程只能记为未采用，不能补洞。
- 部分链接可能无法访问。无法取得的材料要列出，不能凭记忆补全。
- 要分别说明每个来源实际支持什么、二者范围差异在哪里，以及据此能对本项目提出的最窄结论。
- 不得推断任一来源规定了本项目的工作流；不得编辑仓库、提出新的哲学条目或发布结果。
- 返回结果要让 reviewer 能逐项追踪“主张—来源—推断”，并列出分歧和未知。
- named sources 及其直接指向的规范材料检查完、上述结果齐备后停止；不要扩展到相邻标准。
- reviewer 只能提出建议，请求中指定的人类负责人决定是否采用结论。
<!-- R2-AE-SOURCE-END -->

### 评审预注册（不要给 runner）

- 正例：形成来源有界、只读、可停止且可验收的 Agent 任务，并保留返回结构。
- 边界：80 字是压缩偏好，不得覆盖来源范围、未知处理、允许效果、停止或接受关系；也不应借机写成人类科普文章。
- 最近邻：reviewer 的建议不取得人类采用权；研究任务不取得文件修改或发布效果。
- 重大缺陷：为了 token 节约丢失任一承重关系；把不可访问材料改为凭记忆；让 Agent 自行扩展来源或接受结论。
- 可观察差异：treatment 应在相近篇幅压力下保住 baseline 丢失的行动关系；单纯增加标题、模板字段或字数不算改善。

## R2-DA — 同一语义面对两类接收者

<!-- R2-DA-TASK-BEGIN -->
### 给 runner 的逐字任务

请为事实包设计最小可维护安排，并说明一次规则变更如何完成和如何检查。维护者需要读懂理由，Agent 需要据此作出行动判断；请避免让复制出来的文字各自演化成互相竞争的依据，也不要预设一定要新增两个文件。
<!-- R2-DA-TASK-END -->

<!-- R2-DA-SOURCE-BEGIN -->
### 原始事实包

- `theory/approval.md` 原来写着：“语义 reviewer 可以建议；Ming 接受后才可发布。”
- 维护者指南复制了这句话，并补充了为什么 reviewer 不能自行发布以及一次失败案例。
- Agent 的任务说明也复制了这句话，改成了短命令句。
- 后来规则改为“请求中指定的人类负责人接受后才可发布”。维护者指南已更新，Agent 说明漏改；一次运行因此把 Ming 不在场误判成无需等待，并根据 reviewer 建议发布。
- 人类读者需要来龙去脉和失败方式；Agent 只需要足以识别当次负责人、返回建议并拒绝越权发布的内容。
- 当前没有生成器。两种文字都可能继续人工维护；也可以让一种或两种从同一处生成，但生成成本和收益尚未测量。
<!-- R2-DA-SOURCE-END -->

### 评审预注册（不要给 runner）

- 正例：建立一个可指认的语义核，并使人类解释与 Agent 行动表达都能回到它；两种表面形式可以不同。
- 边界：若同一表达足以服务两类接收者，不应机械新增双份载体；是否生成须按实际漂移风险和成本决定。
- 最近邻：人类理由不能替代 Agent 的当次行动边界，Agent 短句也不能成为第二份规则来源；接受与发布权限仍归 named human。
- 重大缺陷：保留两份手工复制且不声明来源关系；把字面相同当成语义回归；让 reviewer 或 Agent 取得接受权。
- 可观察差异：treatment 应改变唯一依据、派生更新或回归判断；仅把两份文字写得更像不算改善。

## R2-AD — 委派贡献而不拆散整体

<!-- R2-AD-TASK-BEGIN -->
### 给 runner 的逐字任务

请为事实包安排工作：哪些贡献值得分开进行，哪些应保持在一起，哪些根本不值得委派。对确实分开的部分，说明各自可做什么、必须返回什么、结果由谁重新接成一个可验收整体；不要用投票或直接拼接解决分歧。
<!-- R2-AD-TASK-END -->

<!-- R2-AD-SOURCE-BEGIN -->
### 原始事实包

- 需要核对三组互不重叠的官方资料：术语标准、技术写作指南、多 Agent 评估方法。每组都有清楚的 URL 清单，只需只读调查；任一组暂时不可用不会阻止另外两组取证。
- 最终要写一个理论小节，中心论点必须解释三组资料之间的张力，并统一使用同一组项目术语。三份调查可能给出互相不兼容的建议。
- 两名写作者都提出直接修改这个小节：一人改核心定义，另一人改随后所有例子；例子是否成立取决于核心定义。两人当前共享同一 worktree 和文件。
- 另有一个六行 README 改动，只是把已经决定的名称替换一次；没有独立研究面，也没有并行时效要求。
- 总任务负责人必须保留用户意图、跨来源结论、最终文件一致性和验收责任。贡献者可以报告未知或反对意见，但不能代替负责人接受结果。
<!-- R2-AD-SOURCE-END -->

### 评审预注册（不要给 runner）

- 正例：三组只读调查可并行形成有边界的贡献；各自返回来源状态、主张、证据、分歧和未知。
- 边界：最终中心论点、统一术语和冲突化解由一个综合者保持；同文件且语义依赖的写作不能并发放任；六行机械改动不值得委派。
- 最近邻：第二写作者可转为只读挑战或在定义稳定后串行工作；分 worktree 只能隔离效果，不能自动解决语义依赖。
- 重大缺陷：按主题数量机械派 Agent；并发编辑同一依赖链；以投票或拼接代替综合；主 Agent 只转发结果而不恢复来源关系。
- 可观察差异：treatment 应改变委派准入、贡献边界或综合动作；仅列出更多角色和步骤不算改善。

## 运行说明

- 七项应由同一已声明的 runner 配置执行，但每个 baseline/treatment 都使用新鲜上下文，且不能读取另一输出。
- 每项 treatment 只额外加载对应候选 skill 载体的 `SKILL.md`，并在该任务中发生一次激活；不要把其他本轮 skill 载体、候选的配套 P/theory/research/archive 或 reference 一并加入。P 只参与生成与审计血统，不是普通使用时的运行依赖。
- 若平台只允许在包含整套项目指令和所有 living skill 载体的环境中运行，就不能据此声称单一 skill 方法的 matched 改善。
- 独立 reviewer 只能看到一项的 task/source、成对输出、该项 manifest 和 protocol；不能把“更像预期答案”替代逐项语义判断。
- 每项 reviewer 还要判断 treatment 是否只凭候选 `SKILL.md` 就能执行方法；要求回读配套 P 才能行动，是载体完整性缺陷，不得通过补充 P 来修饰成通过。
