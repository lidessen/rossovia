# Default autonomy with post-hoc correction

> 中文工作指称：默认自治与事后纠偏。当前为通用 harness design candidate，不是已接受的运行时协议、
> 人工审批门、skill 或 base 实现。它说明人与独立运行 harness 的默认关系；具体硬保证仍由 runtime/base
> 或已有 effect owner 负责。

## 核心原则

Harness 的默认模式不是“每个不确定点先请示”，而是：

> 系统凭已有常识、稳定方法和当前上下文，自主处理绝大多数局部事情；小错通过观察、纠偏和经验
> 吸收解决；只有可能改变整体方向、价值判断、权限关系、共享基线或造成重大不可逆后果的事情，才
> 打断人，请示后再继续。

人不是每一步行动的共同驾驶者，而是少数重大分叉、价值选择和不可逆效果的 owner。独立运行不等于
没有 owner，也不等于系统获得无限授权；它表示 owner 不在普通行动的关键路径上。

## 它解决的真实问题

过度事前审批会把人的负担集中在行动开始前：人必须预先写完大量边界，系统还会把常识重复注入每个
任务、角色和阶段。过度自治的另一端则把“事后纠偏”误解成任意造成外部伤害后再道歉。

本候选保留中间关系：

```text
stable common sense + current context
              │
              ▼
        autonomous local action
              │
      observation / mismatch
              │
              ▼
  correction, rollback, or experience update
              │
              ├─ ordinary local matter → continue
              └─ direction/authority/irreversible matter → ask owner
```

“事后纠偏”只有在影响可观察、可限制、可回退或可补偿时才是合适的主模式；它不是对不可逆伤害的
豁免。

与“主观能动性”研究的关系是：默认自治提供低风险局部行动的许可背景和纠偏缓冲，但不自动产生值得
推进的候选。候选仍需来自目标关联的现实缺口；行动后的观察和结果必须改变下一判断，并且能让 Agent
重建自己的选择与后果之间的联系。唤醒、轮询或更多工具调用只提供机会，不构成主动性证据。相关研究
暂称这组关系为 `goal-linked action loop`；它不是本候选的新状态或权限层。

## 常识、上下文与人工负担

常识类方法不应在每次调用中重新声明。它们应作为 harness 的稳定背景，由模型已有能力、已经接受的
方法、长期经验和环境事实共同提供。任务只补充当前场景真正不同的 delta。

这不要求把所有常识预先写成一份穷尽的授权清单。常识的作用是让系统可以先处理低影响、局部、可逆
的问题；它不是为每一个可能动作生成一条批准规则。

只有出现以下变化时，才需要把背景原则提到前景或请求人介入：

- 目标、范围、优先级、价值取舍或接受条件可能改变；
- 谁可以决定、谁承担后果或系统可以做什么可能改变；
- 共享规则、基础协议、长期基线或跨环境不变量可能改变；
- 外部效果难以撤销、影响面大，或无法可靠观察和纠偏；
- 当前判断超出系统已有常识和方法能安全覆盖的范围。

“不知道”本身不等于必须请示。低影响且可回退的不知道，可以先做最小实践并观察；高后果且不可回
退的不知道，才构成事前请示条件。

## 独立运行的四种关系

独立运行 harness 同时具有四种不同关系，不应把它们压成一个审批状态：

1. **普通运行：** 在已有常识和当前任务关系内，自主观察、判断和行动，不等待人工逐步确认。
2. **事后纠偏：** 发现偏差后自主止损、修复、回退或调整局部方法；不因为犯过小错就把所有后续动作
   升级为人工审批。
3. **重大事项请示：** 识别出方向、价值、权限、共同基线或不可逆效果的变化，形成尽可能短的选择题，
   只暂停受影响的分支。
4. **经验吸收：** 判断一次修正是否只是当前任务补丁，还是可在多个场景复用的方法；复用范围扩大时
   增加相称的验证，不自动把一次纠偏写成全局规则。

人工的正常交互应主要是少量重大选择、纠正方向和接收异常摘要，而不是反复提供常识或审批局部动作。

## 重要方法的复述：用 token 换专注

默认不重复全部背景，并不意味着重要方法永远只出现一次。长任务、上下文压缩、角色交接和错误恢复
都会让承重方法在局部行动中被稀释。遇到这种风险时，harness 可以有意识地花少量 token 做一次
`focus refresh`：从当前 canonical source 选择最可能影响下一判断的少数方法，形成短的 `focus anchor`，
让 Agent 重新对准目标、边界和下一检查。

`focus anchor` 不是新的事实权威、记忆协议、批准记录或运行时状态。它是可丢弃的当前投影，至少保留：

- 当前目标或要解决的具体问题；
- 会改变当前判断的关键方法，以及遗漏它最可能造成的错误；
- 当前角色能做与不能做的边界、未知和不可越过的效果边界；
- 下一步行动，以及观察、停止、纠偏或回返的条件。

### 触发与增量刷新

`focus refresh` 的触发由语义边界而不是固定轮数或调用次数决定。典型触发包括：

- 开始或恢复一段工作，尤其是经历 context handoff、压缩或进程恢复之后；
- 角色、consumer、任务场景或主要目标发生变化；
- 进入 checkpoint、重大决定、owner return 或一次明显纠偏之后；
- 停止并把工作交给另一个行动者，且对方需要知道当前重点才能安全接续。

角色或场景变化时，保留仍然有效的共同方法，只刷新 role/scene delta；稳定常识、无关方法和完整历史
不重新倾倒。若当前场景没有新的遗漏风险，或复述不会改变下一步行动，就跳过 refresh。因而“定期”
指在足以改变注意关系的边界上复述，不是每次调用或每个工具动作都机械重复。

选择重点时优先看：忘记后是否会改变目标、越过权限/效果边界、损失证据、阻断纠偏或误导下一交接；
再用复述成本和当前风险权衡。复述本身不是行为正确或专注已经发生的证据；如果事实、权威或目标发生
变化，canonical source 优先，旧 anchor 必须失效或刷新。需要跨重启、并发、不可信调用者或外部效果中
仍成立的属性，仍属于 runtime/base，而不是靠反复文字获得保证。

## “大事”的判断边界

“大事”不是要求每个项目预先维护一张详尽清单，而是由几个稳定关系共同判断：

| 判断关系 | 小事的典型形态 | 大事的典型形态 |
| --- | --- | --- |
| 目标 | 改善当前路径、表达或局部结果 | 改变要解决的问题或成功含义 |
| 影响 | 单任务、局部、可撤回 | 跨任务、跨主体、长期或难以撤回 |
| 权威 | 在已有 owner/方法范围内工作 | 改变 owner、权限、接受或责任关系 |
| 规则 | 修复一个实例或局部方法 | 改变共享协议、base、长期默认行为 |
| 后果 | 可观察、可停止、可回滚 | 外部不可逆、难以观察或可能扩大伤害 |

这些关系是系统的通用判断背景，不是要求用户为每次运行补填的表单。系统无法区分且潜在后果重大时，
应暂缓受影响动作并请示；系统无法区分但后果局部可逆时，应先做最小实践。

## Candidate 的位置与流转

Candidate 是对“怎样改善当前关系”的可失败假设，不是待审批的愿望、运行时状态或自动获得权威的
新规则。它可以由系统从错误、低效、用户纠正、重复冲突或新证据中自主产生。

```text
observed mismatch / correction
          ↓
local change candidate
          ↓
bounded attempt and observation
          ↓
retain baseline / correct / adopt locally / reopen
          ↓
repeated cross-context pattern
          ↓
reusable method candidate
          ↓
only if shared direction, authority or hard guarantee changes:
owner decision or theory/runtime route
```

按影响范围区分三类 candidate：

- **local correction candidate：** 只影响当前任务或局部工作，默认自主尝试，结果不好就回退或换方案；
  不需要先让人批准。
- **reusable method candidate：** 同类偏差反复出现，可能沉淀为 skill、方法或默认实践；先在真实
  consumer 中观察和比较，是否晋升取决于重复性、边界和维护收益。
- **constitutional candidate：** 可能改变目标、价值、权限、共享协议、base 或不可逆效果；先形成
  紧凑 decision package，得到相应 owner 的选择后再改变。

候选的证据处置可以沿用 `adopt`、`adapt-and-retest`、`retain-baseline`、`no-proposal`、`rollback`
和 `uncertain`，但这些是证据/设计处置，不是每个局部动作都必须经过的人工门。

## 事后纠偏闭环

默认纠偏应尽量在系统内部完成：

1. 发现结果与目标、约束或既有方法不一致；
2. 在已有能力内限制影响，必要时停止、回退或补偿；
3. 区分偶发错误、当前上下文问题、重复方法缺口和上游目标改变；
4. 形成最小 correction candidate；
5. 在当前任务或隔离范围内验证；
6. 保留 baseline、观察、未知和回退关系；
7. 只在重复出现或影响范围扩大时，考虑沉淀为可复用方法或上移到更高 owner。

系统可以自主纠正自己产生的局部工作，但不能用“自我纠偏”代替 owner 的价值选择、接受、发布或
不可逆授权。已经越过硬边界的效果，应先止损和报告，不能把事故重写成普通 candidate。

## Owner-facing progress 的正确位置

`owner-facing-progress` 是本候选的例外通道，不是默认运行流程。只有在以下情况下才准备 decision package：

- owner 的选择本身会改变重大目标、权限、共享基线或不可逆效果；
- 没有该选择就无法安全继续关键分支；
- 先恢复目标场景、提出方案和取舍，确实能显著降低一次重大请示的交互成本。

如果只是普通 owner 暂时不可用、问题局部可逆或当前工作可以继续，则保留必要 unknown，直接推进并在
事后检查，不为了形式完整额外制造 package。owner 返回时，只回接真正改变当前判断的 decision delta。

第一视角和 focus refresh 只在相应语义边界附近使用；常识和稳定方法不应在每次调用重复倾倒。前者服务
场景与责任恢复，后者服务重点方法的保持；两者都不能替代当前 source、实际观察或必要的 owner 决定。

## 与 runtime/base 的边界

这项理论规定人与 harness 的默认工作关系，不凭文字创造安全保证。若“事后纠偏”要在进程重启、并发、
不可信 caller 或外部效果中仍然成立，必须由 runtime/base 或 effect owner 提供相应的身份、隔离、记录、
取消、恢复、回滚或权限能力；理论只能提出该机制需求，不能假装已经存在。

相反，如果问题只是 Agent 在常识性局部判断上偶尔犯错，且错误在效果逃逸前可见和可修复，应优先改进
方法、上下文、经验吸收或 task expression，而不是增加审批门、queue、registry 或强制 workflow。

默认自治的“大事”判断依赖关系性设计：局部 candidate 是否会改变上游目标、横向 authority、下游 effect、
共享基线或采用后纠偏关系，应按 [`relational-verification-design.md`](relational-verification-design.md)
的最小关系视图判断，而不是把一份孤立的局部说明当作完整授权。

## 当前 standing 与检验

当前 standing：`design-candidate / source-bounded / concept-boundary-observed / behavior-unverified /
acceptance-pending / carrier-not-selected`。

最小检验应覆盖：

1. 低风险局部任务是否无需重复常识或人工批准即可推进；
2. 小错发生后系统能否自行发现、回退或修正，而不把后续全部动作锁死；
3. 只有目标、权限、共享基线或不可逆后果变化时才进入请示；
4. 用户纠正能否成为后续行为的来源，而不要求用户反复重述同一常识；
5. 重复纠偏是否能在有证据时沉淀为方法，同时不把一次补丁泛化成全局规则。

这些是跨 harness 的设计问题，不证明已有 planning/WorkCell consumer 已改善，也不证明需要新 runtime。
在出现真实 consumer、匹配 baseline、独立 review 和采用后观察前，不创建专用 skill carrier。
