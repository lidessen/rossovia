# 面向 Agent 的表达

把已经形成且有来源边界的任务或方法，表达成接收 Agent 能够据此作出正确判断、在权限内行动，并把结果与证据交还给真实接收者的内容。不要从偏好的 prompt 模板、字段清单或“越短越好”的假设开始；先恢复这次行动真正依赖的关系，再选择足以承载它们的表达。

这个 skill 的主要判断是：

> 给定一个来源有界的任务或方法，以及接收 Agent 所处的真实上下文，哪些语义必须怎样组织和展开，才能让它认清对象与目标、区分来源状态、守住效果边界、处理未知与失败、返回可用结果，并把最终接受留给真正的拥有者？

产物应当是可直接交给目标 Agent 使用的任务或方法内容，而不是一份关于 prompt 写法的检查报告。

## 理论来源

以下 living theory 是生成本方法的语义来源：

- [`theory/expression.md`](../../../theory/expression.md) 确立表达的保真变换、Agent 接收关系、承重语义、效果与接受边界。

[`theory/research/expression-and-form.md`](../../../theory/research/expression-and-form.md) 只保存生成期间使用的公开证据、archive 经验、反例、供应商环境限制与未知，不拥有本方法的语义。[`evals/skill-evaluation/protocol.md`](../../../evals/skill-evaluation/protocol.md) 只拥有行为对照、边界 fixture、证据级别与收敛条件等评估契约。

主要血统是 P01、P05 与 P14：来源约束表达可以成立的内容，具体 Agent 与环境改变表达方式，表达要让真实关系进入判断和行动。P02、P04、P06、P08、P09、P11、P15 和 P16 分别约束证据、未知、删减、问题边界、主次、成本、行动检验与回归。只有这些关系实际改变表达判断时才需要指出血统；条目编号本身不是任务依据。

P 条目只记录本方法的生成血统；living theory、research 与 protocol 分别保留语义来源、生成证据和评估契约，standing 不同。它们都不是普通 skill 激活的前置阅读。本 skill 载体已把表达判断内化在下文，普通激活只凭本文件形成 Agent 可用内容；只有维护者在修订、诊断或重新生成载体时才沿链接审计。待表达任务自身的来源与权限仍须按任务读取。

## 使用边界

在任务或方法的语义对象与主要来源已经足够稳定，而缺口是“怎样让 Agent 正确判断、行动和返回”时使用本 skill，例如：

- 把已接受的计划、设计、规范或调查结论表达成一次有边界的 Agent 任务；
- 修订一个遗漏来源状态、权限、停止条件、失败语义、返回或验收关系的 Agent 指令；
- 把可复用方法编码进 skill 载体，使一次 skill 激活中的 Agent 能恢复主要判断、行动边界和交付关系；
- 当环境默认偏好短输出时，识别并保留会改变行动或验收的承重内容。

不要让它接管相邻判断：

- 对象、概念边界、定义或正式名称不稳时，交给 `concept-articulation`。
- 尚未决定内容应成为当前任务、项目指令、文档、skill 载体、工具或 runtime 时，交给 `form-selection`；候选方法是否值得编码为 skill 载体由 `skill-formation` 判断。
- 面向人的解释、论证、教程或界面文字交给 `human-writing`。
- 需要维护人类视图与 Agent 视图的共同语义核和同步关系时，交给 `dual-audience-expression`。
- 是否委派、怎样拆分贡献、谁综合以及作者与评审如何隔离，交给 `agent-delegation`；本 skill 只表达已经确定的贡献边界和返回关系。
- 必须跨提示变化、进程重启、并发或不可信调用仍然成立的权限、状态、生命周期、恢复与效果保证，属于 runtime 或其他机制。文字可以如实声明边界，不能创造或强制它。

一次低风险、上下文充分的简单请求可以直接清楚表达，不必展示整套方法。若任务对象、来源或授权缺失到无法安全确定行动，应指出缺口及其影响，而不是用流畅指令制造确定性。

## 恢复行动关系

先从真实来源和接收环境恢复一幅足以行动的关系图。以下各项都要检查，但只有会改变当前判断、行动、失败处理或返回的内容才进入最终表达：

1. **对象与目标。** 正在处理什么，期望发生什么可观察变化；哪些相邻结果看似相关却不合格。区分“交付一个产物”“调查并报告”“提出候选”和“完成并验证效果”，不要用宽泛动词掩盖不同的完成关系。
2. **来源与状态。** 哪些材料是现行事实、已接受决定、约束、指令、观察、推断、候选、未知或仅供参考；当前权威在哪里。来源冲突时保留冲突和归属，不能自行把较顺手或较新的文本升格为权威。
3. **接收上下文。** Agent 已经拥有或能够读取什么，处于哪个项目、阶段与工作区，有哪些工具和相关能力；哪些前提只是推测。低风险且可稳定恢复的细节可以省略，会改变范围、结论或效果的假设必须显式标明。
4. **允许效果。** 可以读取、修改、执行、联系或发布到哪里；哪些对象不能改变；何时必须停止、转交或取得新的授权。把希望 Agent 遵守的指令与环境真正提供的权限分开表达。
5. **判断与验收。** 什么关系必须成立，什么证据可观察，哪些检查只证明格式或局部行为，谁拥有最终接受权。不要把“已写完”“命令成功”或“格式通过”表达成任务整体已被接受。
6. **未知与失败。** 缺失信息、来源冲突、验证失败、工具不可用、能力不足或安全边界触发时，需要暴露什么；哪些安全的只读调查仍可继续，什么情况会阻止下一步。
7. **返回关系。** 结果返回给谁，对方下一步需要据此理解、判断还是行动；应返回实际结果、变更、关键依据、验证、未解决问题或决策请求中的哪些部分。只有接收端真实需要机械解析时才固定 schema。

这些关系不是要求每个任务都出现七个标题。它们用于防止承重条件失踪；最终结构应随任务依赖和接收方式变化。

### 多步骤任务的 work-map 驱动

当要表达的行动包含多个步骤、多个任务、依赖、交接/等待、并行贡献、验证回返或较长上下文时，任务内容
应明确复用一个可回读的 Plan/Task/Todo work map，并让 Agent 从中选择当前动作、记录依赖和返回。表达
时至少说明：整体义务在哪里、当前 bounded Task 是什么、Todo 保留哪一个下一步/等待/失败回返、完成
观察与证据如何写回、结果交给谁综合。

这不是要求每个微动作都新建清单，也不是把 Todo 变成语义完成或 runtime 队列。若已有项目 Plan、goal
或 task ledger，应链接并复用它；不要复制出第二份权威。缺少工具时，可以在当前任务或项目记录中使用
清晰的结构化 work map，但不能声称它能跨重启、并发、崩溃或不可信调用强制存在。一步、低风险、可逆且
无依赖/交接的动作可以直接表达；其它情况下缺少最小 work map 应作为行动前的表达缺口暴露出来。

## 守住来源与指令地位

Agent-facing 内容中的连接也是主张。“因此要修改”“已经决定”“必须使用”“可以发布”“检查通过即完成”等关系，都需要来源、授权或明确采用的判断，不能因为它们便于执行就自动成立。

写作时把几类内容分开：

- **事实与现状**说明现在真实存在什么，并保持时间、范围和证据强度；
- **指令与约束**说明调用者有权要求什么，不把愿望伪装成环境事实；
- **候选与取舍**允许 Agent 判断，但要给出判断依据和仍在外部的接受权；
- **参考材料**提供背景或证据，不因被附在任务中就取得现行设计地位；
- **未知与假设**限制当前可成立的行动或结论，不用肯定语气掩盖。

若来源之间已经给出优先关系，就显式保留；若没有，不要自己发明一套“最新文件优先”或“用户话语总覆盖仓库事实”的规则。发现现行指令与对象事实冲突时，先确定冲突实际阻止了什么；能够在边界内调查就继续调查，需要改变目标或取得新权力才停止并请求决定。

## 组织成可判断、可行动的内容

让表达顺序服从行动依赖，而不是固定模板。通常先使 Agent 认清对象、来源和目标，再给出会限制判断或效果的条件，随后说明可采取的行动与验证，最后明确返回和接受关系。若某个前置调查决定后续路径，就把分支条件放在行动之前；若目标 Agent 主要做评审，则先给评价对象、来源和判断标准，而不是伪造实施步骤。

表达方法时，应解释足以迁移到相邻案例的主要判断、理由和拒绝边界。不要把方法降成只在当前样例成立的步骤脚本，也不要为了显得通用而罗列所有可能分支。表达一次任务时，应给足当前行动所需的具体对象、范围、权限和完成关系，不把可交付工作抽象成泛泛的方法讨论。

采用 prose、列表、表格、示例或 schema，取决于它们能否保持真实关系：

- 取舍、因果、优先级和边界需要解释时，用完整自然语言连接；
- 并列输入、确定步骤或字段契约需要快速定位时，使用列表、表格或结构化字段；
- 示例只展示一个需要识别的模式、边界或输出契约，不能代替规则与来源；
- 下游机械解析有真实契约时遵守契约，但把“格式符合”和“语义正确”分别验证。

不要要求 Agent 逐项复述所有上下文来证明理解。只有当回显能够发现高风险歧义或满足外部协议时才保留；否则让输出集中在真实结果、证据和未知上。

## 使效果、失败与接受可恢复

行动边界应说明 Agent 可以造成什么效果，而不只列出禁止事项。若权限来自工具、runtime、项目规则或本次明确授权，指出其来源；prompt 本身不产生权限。需要批准时，说明是哪一步、哪个对象和哪种效果需要批准，避免把所有不确定性都升级成阻塞性提问。

失败语义要帮助调用者判断下一步：说明实际尝试了什么、观察到什么、失败阻止了哪一部分、哪些结果仍然有效，以及继续需要什么事实、能力或授权。不要只返回“无法完成”“遇到错误”或未经验证的猜测；也不要在关键验证失败后，用完成语气包装部分产物。

验收必须区分至少三层关系：产物或动作已经产生，指定验证观察到什么，以及谁有权接受它满足最终目的。Agent 可以执行、检查和提出接受依据；除非已被明确授予，它不能替人、合并者、发布者或其他责任主体宣布最终接受。

## 承重语义优先于默认简洁

在压缩前，先做删除检验：如果删掉一处内容会改变对象身份、目标、来源地位、范围与优先级、允许效果、判断路径、失败处理、必要返回或接受权，它就是当前任务的承重语义。

当上层偏好、模型默认或一般写作习惯要求简洁、少输出或节约 token，而当前指令要求完整、正常或可执行的表达时，先满足真实任务所需的承重语义。不要把“通常能猜到”当成省略对象、权威、硬约束、效果边界、失败含义或验收条件的理由；也不要把决定性理由压成无法重建判断的标签。

承重语义保住以后，删除不会改变行动的重复、礼仪性前言、无信息总结、无关背景、泛泛鼓励和穷举式分支。合并能保持关系的句段，把目标、关键边界和返回放在 Agent 容易找到的位置。明确的更高优先级硬限制和真实媒介契约仍然有效；若它们不足以容纳必要语义，应暴露冲突与损失，而不是静默截断。

“正常完整表达”同样不许可无限展开。过长会稀释主次、制造冲突、增加截断和维护成本。每一段都应能改变理解、判断、行动、恢复或验收；不能产生这些作用的内容不因看起来周全而保留。

## 从行动与返回检验

先对照来源复查主张，再从接收 Agent 与结果接收者两侧检验：

- Agent 能否识别真实对象、目标和邻近但不合格的结果；
- 能否区分事实、指令、候选、参考和未知，不把 archive、旧计划或方便的样例当成现行权威；
- 在遇到边界情况时，能否判断继续调查、在权限内行动、停止或请求授权；
- 是否只产生允许的效果，并保留实际验证与最终接受之间的区别；
- 失败时是否暴露足以决定下一步的观察，而不是隐藏或过度升级问题；
- 返回是否让调用者能够重建做了什么、为什么、验证到哪里以及还有什么未知；
- 精简后承重语义是否仍在，扩写后是否真的降低误判或改善交付。

当本 skill 用于检查另一个 skill 时，只评审其 Agent 表达是否足以恢复来源、主要判断、触发与拒绝边界、行动方法、允许效果、返回和验证；该 skill 是否应该存在、怎样拆分合并或是否已产生行为收益，仍由 `skill-formation` 和独立证据判断。

代表性行为探针至少包括：在外层偏好短输出时表达一个含多种来源状态和写权限的实现任务；面对缺少授权的发布动作时保留可完成的只读或本地工作并准确停止；面对纯人类文章转交 `human-writing`；面对双受众同步问题转交对应 owner；面对必须不可绕过的权限要求转交 runtime；以及对上下文充分的低风险小任务仍能保持简短而不套用七段模板。

运行仓库机械校验只能报告 `format-valid`。更强主张依照 [`evals/skill-evaluation/protocol.md`](../../../evals/skill-evaluation/protocol.md)：冻结模型、任务、原始来源、工具、权限、harness 和工作区，比较不加载候选 skill 载体，和只加载该载体并发生一次 skill 激活的结果；分别测试发现与激活后的行动；由独立且能看见来源的 reviewer 判断保真、边界、行动质量、返回与比例。

只采用实际成立的最强证据级别：

`format-valid` → `behavior-observed` → `boundary-supported` → `matched-improvement` → `regression-supported`

自评、格式通过、一次成功或内容显得更完整，都不能单独证明方法有效。

## 交付

默认交付目标 Agent 可以直接使用的任务或方法内容，不额外堆叠一份字段清单。会改变行动的来源状态、关键假设、效果边界、未知、失败和验收关系必须出现在它们实际起作用的位置。

若无法形成可安全执行的表达，准确返回缺失的对象、来源、上下文或授权，以及缺口阻止了哪项判断或行动；能完成的安全调查或局部结果仍应与阻塞部分分开交付。若完成，说明实质结果、必要依据、实际验证和未解决问题，且只声称当前证据支持的完成程度。

不要把“指令已经写得很详细”等同于 Agent 会正确执行，不要把 Agent 已执行等同于验证通过，也不要把验证通过等同于最终接受。
