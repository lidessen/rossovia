### 001A

原话：

> 我们现在设计的迭代循环其实比较像无监督学习；

- 明确内容：用户提出对当前迭代循环的概念判断或类比。
- 推断：可作为理论/架构分析候选，研究“迭代循环与无监督学习的相似性及边界”。
- 未知：具体指哪一个迭代循环；“像”是机制类比、目标类比还是效果类比；是否需要形成正式理论结论。
- 去向：保留为理论/规划候选，暂不进入正式研究结论。
- 需要补问：希望验证哪些相似点？是否存在监督信号、奖励、人工反馈或明确验收标准？
- 后续决定者：当前迭代循环的目标 owner 或项目负责人；若要开展研究，则由研究/理论 owner 决定。
- 回返关系：待明确迭代循环定义和研究意图后再判断是否立项。

### 001B

原话：

> 后续的计划，我们还需要一个开发生命周期的skills套组，覆盖从确定需求，设计，写文档，开发，测试，验证，改进全生命周期；

- 明确内容：提出建立覆盖完整开发生命周期的 skills 套组。
- 推断：属于 incubation/planning candidate，可能包含需求、设计、文档、开发、测试、验证和改进等多个 skill。
- 未知：套组边界、目标项目、使用者、优先级、各阶段的完成/接受标准、维护 owner，以及是否需要与现有 skills 集成。
- 去向：候选进入项目 Plan 或 skills 规划，不视为已承诺开发。
- 需要补问：哪些阶段必须优先覆盖？是一个统一套组还是多个独立 skill？谁负责接受整体设计？
- 后续决定者：项目/skills 负责人决定是否纳入 Plan、范围和优先级；各 skill 的真实 owner 决定具体实现。
- 回返关系：待确认范围、优先级和 owner 后再拆分为正式计划或局部待办。

### 001C

原话：

> 理论/skill的部分完备之后，代码部分还需要一个可以控制变量测试agent行为的实现，比如测试prompt/skill效果，对比模型能力；

- 明确内容：提出实现一个可控制变量、用于测试 agent 行为的代码系统；示例包括测试 prompt/skill 效果和比较模型能力。
- 推断：属于 experiment candidate，可能也是评测 harness 的实现候选。
- 未知：测试对象、变量、baseline、评价指标、模型范围、运行环境、数据集、复现要求，以及“理论/skill 完备”的判断标准。
- 去向：保留为实验/评测实现候选；不创建实际实验记录，也不声称已有测试结果。
- 需要补问：首个实验要控制哪些变量？需要比较哪些模型或配置？什么结果才算有意义？
- 后续决定者：实验设计和证据 owner 决定方法与接受条件；工程 owner 决定实现方案和维护责任。
- 回返关系：待确定最小实验问题、baseline 和指标后，再进入实现或实验计划。

### 001D

原话：

> 还有设计验证，能不能通过prompt让agent从对话模式，变成更接近碎片化思考的模式，就是想法是一个概念一个概念蹦出来的，不是完整的句子。就像是没有经过语言模块处理过的原始想法；

- 明确内容：提出验证 prompt 是否能使 agent 输出更接近碎片化、概念单元式的表达。
- 推断：属于实验候选，目标可能是改变输出形式或内部思考的外在表现。
- 未知： “碎片化思考”“原始想法”的可观察定义；是否只测试输出格式；评价标准；是否允许把这种输出称为思维或意识；安全、隐私和误读边界。
- 去向：experiment candidate，需先进行概念和测量定义；不作为 agent 已产生原始思维的事实。
- 需要补问：希望观察的是词语/概念片段、非完整句输出，还是其他可测行为？如何区分提示造成的格式变化与能力变化？
- 后续决定者：实验/evidence owner 决定操作化定义和证据标准；项目负责人决定是否纳入主线。
- 回返关系：待形成可复现的 prompt、对照条件和评价标准后再决定是否实施。

### 001E

原话：

> 然后基于这个再验证多互斥人格形成的统一自我个体agent。因为我一直觉得人的意识思维高绩性来自于人的大脑中矛盾对立的想法，形成意识流，这个实验的目的是看看能不能复刻；

- 明确内容：提出在 001D 基础上，验证多个互斥人格是否能形成统一的个体 agent；用户同时给出关于人类意识的个人判断和实验目的。
- 推断：属于依赖 001D 的 experiment candidate，也涉及多 agent/多角色协调设计。
- 未知： “互斥人格”“统一自我个体”“形成”的操作化定义；人格数量和边界；统一性的评价方法；与普通多角色协作的区别；伦理、安全和解释边界。
- 去向：保留为实验候选，并标记为依赖 001D、需要较强澄清；不视为已证明意识或人格形成。
- 需要补问：成功标准是什么——行为一致性、长期身份连续性、冲突整合能力，还是其他指标？是否只研究模拟行为，不对意识作本体承诺？
- 后续决定者：实验/evidence owner 决定实验设计与证据条件；项目/Principal 决定是否允许将其作为主线方向。
- 回返关系：只有在 001D 的定义、baseline 和结果解释边界明确后，才适合重新评估本条。

### 001F

原话：

> 另外还有就是基于DeepSeek harness实现的harness 基座，这是一个单一主agent/或者agent team，单一会话，无compact设计而是采用实时记忆和查看聊天记录模式，用通知作为单一输入源代替单一用户消息实现多来源信息处理，轮询todo list实现并发。采用类似gpt live的实时对话设计，两边的输出互不干涉，实现类似人类im聊天的模式，发消息是即时的，改变和影响后续动作。

- 明确内容：提出一个基于 DeepSeek harness 的 harness 基座/架构设想，包含单一主 agent 或 agent team、单会话、无 compact、实时记忆与聊天记录查看、通知作为输入源、多来源处理、轮询 todo list 实现并发，以及双向即时对话。
- 推断：属于架构/implementation planning candidate，可能成为 001C、001D、001E 的运行基础。
- 未知：DeepSeek harness 的具体基线和许可；“两边输出互不干涉”的技术含义；并发一致性、消息顺序、失败恢复、上下文增长、权限边界、取消机制和验收条件；单主 agent 与 agent team 尚未决定。
- 去向：保留为 harness 基座的 incubation/planning candidate，附带潜在实验基础设施关系；不视为已确定架构或已开始开发。
- 需要补问：第一版最小可用范围是什么？采用单主 agent 还是 agent team？实时记忆、通知输入和 todo 轮询分别需要满足什么行为或性能标准？
- 后续决定者：工程/runtime owner 决定架构、实现和可靠性标准；项目负责人决定是否作为共享基座，以及与 001C–001E 的依赖关系。
- 回返关系：待确认基线、最小范围、owner 和验收条件后，再拆为架构设计、实现任务或实验基础设施任务。
