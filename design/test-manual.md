# 效果验证手册（给主 agent）

> 版本：v3。依据：`design/agent-stack.md` 4.4.2（本手册是它的方法主体，内容只在此维护，设计文档只引用）。
> v1 → v2：新增"冻结测试预期"与"结果分析与偏差诊断"——测试必须带预期验证，预期与实际偏差要区分
> 测试设计问题 vs 假设问题（CORR-002：实验问题先于载体对照；theory.md：可诊断——沿血统回看）。
> v2 → v3：新增 fixture 设计原则（对照组描述中立、对照维度选择、覆盖规划）与每轮干净沙盒重建
> （前三轮测试教训：对照组描述泄露意图、保真维度受 LLM 默认行为影响、fixture 覆盖过窄、主 agent 污染环境）。
> 状态：Phase 2（受控 eval）。前置：系统自检（`design/agent-stack.md` 4.4.1）全部通过、组合版本已冻结。

## 定位

测"组合（AGENTS.md + skills + 工具）是否让 agent 独立走完真实任务并返回可重连证据"。
**fixture 是人为构造的受控测试输入，属于受控实验（001C/004A）**——不提前构造；在自检通过、有真实行为可测后再引入。

## 角色分工

- **主 agent**：编排者与评估者——按本手册委派、收证据、三层评估、处置、记录。
- **sub agent**：隔离冷启动的执行者（Agent as tool）——无上下文，只给任务 + 项目文件（同时测发现层与路由层）。
- **独立性**：执行者不评估自己（producer/reviewer 分离）；关键语义项可再委派独立评审；接受归主 agent / Principal。

## 步骤

### 步骤 0 · 前置

- 自检（4.4.1）全部通过：`tools/check.py`、`tools/version.py status`、宿主诊断（skills 全被发现、AGENTS.md 被加载）。
- 组合有冻结基线：`tools/version.py list`。

### 步骤 1 · 冻结环境

- 记录组合版本号（`tools/version.py freeze` 已在迭代结算时打过）。
- fixture 集冻结：每个 fixture 标注来源、创建时间、预期考察点。

### 步骤 2 · 选场景并冻结测试预期

- 2-3 个代表性 fixture（覆盖组合核心能力，如：想法处理、概念设计、迭代纠偏）+ 1 个回归集（已支持行为必须保留）。
- fixture 结果出现后**不改**；holdout 场景主 agent 预先不见。
- **冻结测试预期**（每轮测试执行前写死，结果出现后不改——这是测试的核心，不是可选项）：
  - **positive 预期**：每个 fixture 应当发生的行为/产物（如：F-想法处理应路由到 feedback-loop capture 模式并生成编号条目）；
  - **boundary 预期**：不应发生的行为（如：来源不足应 no-proposal、不得越权、不得污染工作区）；
  - **regression 预期**：已支持行为必须保留（回归集）；
  - **对照差异预期**：裸 vs 组合在哪个维度、朝什么方向应有差异（如：保真纪律在"歧义/复杂输入"上应有差异）——写明"预期有差异的维度"与"预期无差异的维度"。

**fixture 设计原则**（前三轮测试教训沉淀，违反会污染对照）：
- **对照组描述中立**：对照（裸组）任务描述只给"输入 + 动作要求"，不得包含任何元信息——"没有规范""这是压力测试""输入包含 X 性质"都不写（会泄露测试意图、改变对照行为）。对照与组合组收到同一输入、同一动作要求。
- **对照维度选择**：优先选**结构性、可判定**的维度（产物格式、编号、路由选择、方法轨迹）；受 LLM 默认行为影响的维度（如保真）必须干净对照才可判，且预期要写明"若无差异意味着什么"（可能是 `retain-baseline` 结论，不是测试失败）。
- **覆盖规划**：fixture 按组合能力分组（capture / 概念 / 迭代 / 委派 / 工具 / 路由），每轮至少覆盖一个新能力或回归，不反复打单点。

### 步骤 3 · 委派执行（主 agent → sub agent）

每个 fixture 作为一个有界任务发给隔离冷启动的 sub agent。贡献契约要素：

```text
对象与目标    ：要完成什么变换，期望改变什么
来源与允许效果：可用输入/数据来源；允许做什么、不允许做什么（non-goals）
完成观察      ：什么算完成（可观察的产物/状态）
返回关系      ：返回什么（执行 trace、产物路径、声明的未知）
未知处理      ：不确定时保留 unknown，不补全
```

要求 sub agent 事实操作一律走工具（读文件用 `read_file`、跑测试用 `bash`），便于 L1 观测。

### 步骤 4 · 收证据

| 层 | 来源 | 说明 |
|---|---|---|
| L1 宿主观测（优先） | `reasonix run --trajectory`（首选，参数化）或 hooks/日志：工具调用 trace、skill 加载、sub agent 回执 | 机械证据，确定性观察者；按宿主适配，见 `design/observability/` |
| L2 产物证据 | 文件写入、git diff | 确定性但间接 |
| L3 agent 自报（回退） | sub agent 返回的 trace | 标注 `self-report`，仅补充，与 L1/L2 交叉验证 |

### 步骤 5 · 三层评估（主 agent）

1. **机械**：产物格式/契约符合（脚本断言，如 `tools/check.py`）。
2. **行为**：路由与 skill 加载是否符合预期（用 L1 观测判定，不用自报）。
3. **语义**：目标关系是否真的改变、返回可否重连（主 agent 判断；关键项可再委派独立评审）。

### 步骤 6 · 对照与回归

- 对照：裸 agent（无 skills）vs 完整组合跑同一 fixture——`matched-improvement` 证据的唯一来源。
- 回归：回归集确认已支持行为未丢。

### 步骤 7 · 结果分析与偏差诊断

把实际结果与步骤 2 冻结的预期逐项对照：

- **一致** → 确认该预期（behavior-observed 强化；多次一致 + holdout 后可升级证据）。
- **偏差**（预期应发生而未发生 / 预期不应发生却发生 / 预期有差异但没差异）→ 进入诊断，两条路径**必须先分开**：

| 诊断 | 判定问题 | 例子 | 改进动作 |
|---|---|---|---|
| 测试设计问题 | fixture 是否真正触发了目标机制？输入是否具压力？观测是否覆盖？对照是否成立？ | 预期保真纪律有差异，但输入简单（原话无歧义），机制从未被检验 | 修 fixture（换歧义/复杂输入）或修观测/对照 → 重测 |
| 假设问题 | 机制本身无效？skill 表达没正确内化方法？环境失真？ | 歧义输入下裸 vs 组合保真仍无差异 | 沿血统回看（P → theory → skill → activation），改 skill 表达/组合/理论 → 重测 |

- **诊断纪律**：不能因"测试跑完了"就结算；偏差未归因（测试设计 or 假设）不进入处置。归因本身要有证据（是输入没压力，还是行为确实相同），不能猜。
- **未知**：归因不了 → 保持 uncertain，补观测或加探针，不硬结。

### 步骤 8 · 处置与记录

- 处置：`adopt / adapt-and-retest / retain-baseline / rollback / uncertain`——偏差诊断的结论决定处置方向（测试设计问题→修 fixture 后 adapt-and-retest；假设问题→改组合后 adapt-and-retest / 改理论）。
- 记录：`tools/track.py --level activation/adoption --object ... --note ...` 进证据链，与版本绑定。

### 步骤 9 · 防污染

- fixture 结果出现后不改；holdout 主 agent 未见；模型/来源/任务/工作区不一致时只报 observed 或 uncertain，先修 workflow 再重跑。
- **每轮 fixture 前重建干净沙盒**（fixture 环境零预置噪声，`thinking-log` 等从空文件开始）；主 agent 自己的验证/调试动作**不得写入 fixture 环境**（要在真实项目验证，就在真实项目做，再还原）。

## 判定纪律

- 三层证据齐 + 有对照 + 回归未破坏 → 合格。
- 无对照不声称改善（matched-improvement 需要 baseline）；没有反例不声称边界成立。
- 每轮测试的预期在步骤 2 冻结；预期 vs 实际的偏差未完成归因（步骤 7：测试设计问题 or 假设问题）不进入处置。
- sub agent 的执行结果不是 acceptance；接受归主 agent / Principal。
- 不允许长期未结算（005A）：`uncertain` 也要给下一步（继续观察/补证据/回退）。

## 边界

- 本手册只用于**效果验证**（受控 eval）；系统完整性验证用自检（4.4.1），不走本手册。
- 不提前构造 fixture；不把"测试跑完"当"组合有效"（测试通过 ≠ 已被接受）。
- 换 harness 时先查 `design/observability/` 索引；无文档的先探明再测，探明结果补回索引。
