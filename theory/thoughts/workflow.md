# 工作方法、设计修剪与工作流过渡

> 用户关于工作方法演化、设计克制、想法应用闭环与工作流过渡（临时班子/bootstrap）的原始想法。

## IN-2026-08-26-009A — 工作方法持续迭代机制

原文：

> 后面还得更新下工作方法。harness 系统要有机制，在工作到达一定程度时要回顾总结，对现有的工作方法进行改进：差的要改进，好的要肯定。这也是一种迭代，需要设计一个机制，让 goal 驱动的或无限执行的 Agent harness 层能持续自我迭代、滚动更新；随着工作的推进，工作方法也随着改进。

去向：goal-scoped method evolution 候选；在语义 checkpoint/safe point 交汇，保留 baseline、rollback、lineage 与独立 review。

## IN-2026-08-26-010A — 设计回落与修剪

原文：

> 做设计的时候要有一个回落，就是怎么保持克制，有点像树枝自由生长之后的修剪。设计不能只不断增加字段、状态和机制；需要在迭代中回落、删减和收束。比如现在设计的 frontmatter 字段，就需要用这种回落/修剪关系做设计验证和应用。

去向：设计修剪规则——初始设计 review 与实践后回落双时点。

## IN-2026-08-26-011A — 克制也发生在初始设计

原文：

> 这个克制也可以发生在初始的设计阶段，设计完了 review 的时候。

## IN-2026-08-26-012A — 想法如何被验证应用

原文：

> 怎么确保我提的这些想法会被实验验证或者试行应用到后续的 work 中呢？

## IN-2026-08-26-013A — 担心处理了没走到最后

原文：

> 我总担心会不会处理了但没有走到最后，然后变成归档的资料，完全没有加入到 harness 等实际系统中应用。

去向：012A/013A 形成「应用交接不能被 research archive 吞掉」的边界：semantic handoff → carrier handoff → activation observation → adoption/reopen evidence。

## IN-2026-08-26-017A — 先总结回顾，实践出真知

原文：

> 暂时不推进 WorkCell。当务之急是对目前已有的工作成果和之前的工作历史做总结、回顾和改进；当前成果还没有达到满意程度，需要先梳理一套更合理的工作流。
>
> 不管工作流是正式的、试行的，还是只停留在想法阶段，都要坚持"实践出真知，实践是检验真理的唯一标准"。这意味着不要等形成正式文档后才推行，可以边实践边修正；敏捷开发取代瀑布式开发的道理也在这里。
>
> 需要发动多个 agent，全面整理更合理的工作流：把简要版本放在 `AGENTS.md`，详细版本放在 harness 文档；再整理这条工作流上的 skills，明确 skills、harness 文档和理论文档的边界；基于这套工作流重新设计项目结构，迁移文件、形成更多 skills 和文档，之后再设计并实现 WorkCell。
>
> 需要先为"到 WorkCell 设计和实现之前"的工作规划一个 plan，包括 agent 数量、分工和推进方式；这是第一阶段，第一阶段的目标是梳理下一阶段可用的工作流。

## IN-2026-08-26-018A — 打回重来：引火/引信与临时筹备

原文：

> 打回重来。现在遇到的问题类似"引火"或"引信"问题：就像氢弹需要原子弹引爆；更接近的例子是，中华人民共和国建国需要一个临时的筹备委员会或过渡政府。

解读：不能直接把最终 workflow design 当作当前工作方式；需要一个能组织已有成果、启动第一轮实践、承担临时协调与边界控制、条件成熟后向正式结构交接的过渡机制。

## IN-2026-08-26-019A — 点火装置设计问题

原文：

> 启动的点火装置设计得还是有问题。临时委员会本来就是照着正式形式去组织设计的，现在显然没有任何设计和 skill 指导，所以出现了不少问题。比如 `harness-workflow` 的设计问题就比较多。它能算正式 design 吗？为什么 design 里面会有"为什么这次要重写"之类的表述？即使要写，也应该放在背景介绍部分。由此可以判断，前置的筹备工作实际上没有做好。

解读：临时委员会是正式组织形态的受限、可退出实例，不取消角色、对象、权责、流程、交接和 skill 指导；正式 design 应保持干净的规范性主体，历史、重写原因、审计过程和证据回顾进背景/research/records。

## IN-2026-08-26-020A — 临时筹备目录

原文：

> 我的建议是在一个临时筹备目录下组织你需要的东西。当然，这个临时筹备目录最后是要保留归档的。这个筹备项目应该是从现有的所有素材中拼凑出一套完整的班子。

解读：临时筹备目录是有边界、有 owner、有交接和归档出口的临时筹备项目；结算后保留为只读归档，供复盘与失败路径恢复。

## IN-2026-08-26-021A — 临时班子内容是 skills 和 AGENTS.md

原文：

> 临时班子的内容实际应该是 skills、`AGENTS.md` 之类的东西。

解读：筹备项目由能被 Agent 实际加载和执行的载体组成（临时 `AGENTS.md`、选定的 `.agents/skills/`、必要脚本/工具及其边界说明），不是文档中描述"应该有谁"。

## IN-2026-08-26-022A — 临时班子目录放根目录

原文：

> 临时班子目录放在根目录。

解读：临时班子是根目录下可被 Agent 作为临时项目进入、加载和执行的工作单元；`planning/` 只保留 plan、standing、过渡触发与审计记录。

## IN-2026-08-26-023A — 临时班子的 skills 是工作流 skills

原文：

> 临时班子的 skills 设计明显是不对的，难道不应该是工作流中会用到的 skills 吗？

解读：临时班子装配的是正常 workflow 实际会用到的 skills（capture、问题/概念、复杂度与工作量、形式选择、委派、Agent 表达、机制复核、实践回返、skill 形成等），不是"组装班子"的元 skill。

## IN-2026-08-26-024A — bootstrap 是 AGENTS.md + skills

原文：

> `bootstrap` 的内容和形式完全不对。可以理解成 `bootstrap` 里面主要就是 `AGENTS.md` + skills，就是 Agent 怎么去开发这个项目的；可以理解成这是用老的项目孵化下一代项目。

解读：bootstrap 是可进入、可加载、可执行的下一代项目孵化工作单元，主体是指导 Agent 开发本项目的 `AGENTS.md` 与 workflow/development skills；旧项目的理论、经验、约束和工具是来源。

## Roadmap 当前主序列（用户方向）

1. 回顾已有成果与工作历史，形成可实践、可回退、边实践边修正的工作流；
2. 按真实 consumer、owner、边界、证据和回退关系，收敛结构、文档和 skills；
3. 继续迁移有价值的文档和 skills，形成需求、设计、文档、开发、测试、验证、改进相关的项目内方法 skills；
4. 在前置工作流和结构达到可审查出口后，反复打磨并完成 Work Cell 协议设计；
5. 在 Work Cell 边界之上设计基于 DeepSeek Harness 的工作系统；
6. 两层设计通过明确评审后，建立实现计划并实现系统；
7. 在已实现的工作系统上承载各类 harness 构想，按 experiment/eval 边界逐个验证。
