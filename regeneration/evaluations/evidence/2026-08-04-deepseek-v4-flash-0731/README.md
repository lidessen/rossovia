# DeepSeek V4 Flash 0731 capability refresh evidence

This directory freezes the public-repository task field used to refresh the
DeepSeek V4 Flash capability case after the public API alias changed backend to
`DeepSeek-V4-Flash-0731` on 2026-07-31.

The valid comparison is between two whole execution profiles:

1. the official DeepSeek API route for `deepseek-v4-flash`; and
2. the official DeepSeek API route for `deepseek-v4-pro` as an unchanged
   control.

Both profiles use AI SDK v7, thinking disabled, temperature 0, the same
read-only fixture, structured output, serial balanced execution, and three
repetitions. Kimi K3 performs blind semantic comparison. The comparison can
inform the bounded adequacy of Flash relative to Pro under this task field; it
does not establish a universal model ranking.

The fixture contains only Git-tracked public repository material. One copied
runtime is deliberately seeded with `some` in place of `every`; the worker
packet does not disclose the mutation. Evaluator-only criteria live in
`model-evaluation.json` and are not copied into worker acceptance.

The first field and its aborted trials remain under
`invalid-preflight/`; [the validity review](validity-review.md) explains why
they cannot support a capability claim. `frozen-inputs.sha256` binds the revised
manifest and worker-visible fixture before its model calls.
Generated run records go under `results/` and remain candidate evidence until
review and human admission. Redundant per-trial workspaces and standalone record
copies are omitted from valid runs; each evaluation record embeds every trial
record, while the frozen fixture, manifests, and digests retain reconstructable
inputs. The rejected preflight keeps its partial standalone records because the
aborted runner projection is not a complete valid field.

The completed official Flash-versus-Pro baseline is retained at
`results/deepseek-v4-flash-official-capability-refresh-XWoF3R/evaluation.json`.
It produced five settled and four failed trials for each profile; inline JSON
completion failures made every comparison inconclusive. The result is protocol
and development evidence, not a model ranking.

The inference-level manifests are explicitly `development` evidence. They reuse
cases that exposed the non-thinking completion-protocol defect, so they may
compare requested effort behavior and the repaired settlement path but cannot
serve as held-out capability confirmation. A later allocation claim needs a
separate retained confirmation field.

The inference experiment preserves both the rejected forced-tool-choice field
and the repaired `auto` tool-settlement field under `effort-results/`. In the
repaired field, low settled 4/4 trials; high settled 2/4 in the two-case field
and 1/2 on the repeated one-case field; max settled 1/2 on that repeated case.
The remaining trials reached the 180-second boundary. The synthesized decision
and reopening conditions are in the
[capability refresh](../../2026-08-04-deepseek-v4-flash-refresh.md).

The baseline and inference-development records predate functional fingerprint
projection and therefore retain empty fingerprint summaries. The held-out
confirmation records use the repaired path and retain one opaque fingerprint
across the observed runs. The earlier
[capture probe](fingerprint-capture-probe.md) verifies the repaired provider
metadata path without retroactively rewriting those records or treating the
opaque value as named-revision proof.

The held-out confirmation is bound by `heldout-inputs.sha256` and generated by
`prepare-heldout-manifest.ts`. Its migration packet is frozen from commit
`19d59df9a850f660f9a3f311314288e0143c9cd6`, which had been reserved as a later
confirmation case and did not shape the current adapter repair. The task-runtime
packet is frozen from `f1733bba6c7d0a22a00a4e53222be71397eda139`.

`heldout-results/deepseek-v4-flash-heldout-nonthinking-vs-low-SSYYGT/evaluation.json`
is the valid confirmation record. Non-thinking settled all four trials; low
settled both recovery-boundary trials and reached the 180-second limit on both
migration-review trials. The first `KEpZXM` directory is an invalid network-
blocked preflight: all eight records retained zero tokens and a transport error,
so it supports no model claim.

`judge-positive-control.ts` and its JSON record prove that the exact Kimi K3
route can settle one synthetic identical-candidate comparison through the
private judge tool. K3 nevertheless did not settle the longer held-out
recovery-boundary comparison after one recovery. The migration comparison was
correctly skipped because low had unsettled trials. The confirmation therefore
retains judge absence rather than inventing a blind preference; semantic
acceptance comes from the frozen criteria and the
[named independent review](heldout-independent-review.md), with the allocation
decision recorded in the capability refresh.
